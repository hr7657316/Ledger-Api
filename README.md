# Transaction Ledger API

A simple backend API for a transaction ledger. You can create accounts, add credit and debit transactions, view balances and paginated history, and transfer money between accounts.

**Tech stack:** Node.js + Express + SQLite (through `better-sqlite3`).
SQLite stores everything in one file, so you don't need to install or run a database server.

---

## 1. How to run

Requirements: **Node.js 18 or newer**.

```bash
npm install      # install dependencies
npm start        # start the server at http://localhost:3000
npm test         # run the automated tests (uses an in-memory DB)
```

Optional environment variables:

| Variable  | Default     | Meaning                     |
|-----------|-------------|-----------------------------|
| `PORT`    | `3000`      | Port the server listens on  |
| `DB_FILE` | `ledger.db` | Path of the SQLite file     |

To start over with an empty database, stop the server and delete `ledger.db*`.

## 2. Project structure

```
ledger-api/
├── src/
│   ├── server.js          # Starts the HTTP server
│   ├── app.js             # Express setup + central error handler
│   ├── db.js              # Opens SQLite, creates tables, constraints and triggers
│   ├── ledger.js          # Business logic (accounts, transactions, transfers)
│   ├── validators.js      # Input validation
│   ├── errors.js          # ApiError class, so every error has the same shape
│   └── routes/
│       ├── accounts.js    # /accounts endpoints
│       └── transfers.js   # /transfers endpoint
├── tests/api.test.js      # End-to-end API tests
└── README.md
```

A request flows like this:

```
route (routes/*.js) → validate input (validators.js) → business logic (ledger.js) → SQLite (db.js)
                                    ↓ any error thrown
                        error handler in app.js → consistent JSON error
```

## 3. How data integrity works

| Requirement | How it is done |
|---|---|
| **Atomicity** | Inserting the transaction row and updating the balance both run inside `db.transaction(...)` in `ledger.js`. If anything throws, SQLite rolls back **both** changes. |
| **Atomic transfer** | The debit and the credit run in **one** database transaction. If the credit fails (for example a duplicate reference), the debit is rolled back too. A partial transfer cannot happen. |
| **Balance never negative** | The debit runs `UPDATE ... SET balance = balance - ? WHERE id = ? AND balance >= ?`. If it changes 0 rows, the balance is too low. The DB also has `CHECK (balance >= 0)`. |
| **Failed transactions don't affect balance** | Validation runs first, and any later error rolls the whole DB transaction back. |
| **Immutability** | The API has no update or delete endpoints for transactions (`PUT`/`PATCH`/`DELETE` return `405`). Database **triggers** also block `UPDATE`/`DELETE` on the `transactions` table, even from direct SQL. |
| **Unique reference per account** | `UNIQUE (account_id, reference_id)` constraint in the DB, plus a check in code that returns a clear `409`. |
| **Valid type / amount** | `CHECK (type IN ('credit','debit'))` and `CHECK (amount > 0)` in the DB, plus validation in code. |
| **Account must exist** | `FOREIGN KEY` from `transactions.account_id` to `accounts.id`, plus a `404` check in code. |
| **No floating-point bugs** | Money is stored as **integer cents** (`10.50` is stored as `1050`). The API accepts and returns normal numbers. |

## 4. API documentation

Base URL: `http://localhost:3000`. Request and response bodies are JSON (`Content-Type: application/json`).

### 4.1 Create account — `POST /accounts`

Request:
```json
{ "name": "Alice" }
```

Response `201 Created`:
```json
{
  "id": "29d8f709-e2fd-4bd1-8846-2e23d3ea13ec",
  "name": "Alice",
  "balance": 0,
  "created_at": "2026-10-27T12:47:37.134Z"
}
```

- `id` and `created_at` are generated by the server.
- The balance always starts at `0`. Sending a `balance` field returns a `400` validation error.

### 4.2 Get account — `GET /accounts/:id`

Response `200 OK`: the same shape as above, with the current balance.

### 4.3 Get balance — `GET /accounts/:id/balance`

Response `200 OK`:
```json
{ "account_id": "29d8f709-...", "balance": 100 }
```

### 4.4 Add transaction — `POST /accounts/:id/transactions`

Request:
```json
{
  "type": "credit",
  "amount": 100,
  "description": "Salary",
  "reference_id": "ref-1"
}
```

| Field | Rules |
|---|---|
| `type` | Required. `"credit"` or `"debit"` |
| `amount` | Required. A number greater than 0, with at most 2 decimal places |
| `reference_id` | Required. A non-empty string, unique within this account (max 100 chars) |
| `description` | Optional. A string (max 255 chars) |

Response `201 Created`:
```json
{
  "transaction": {
    "id": "7ece1477-1e5a-4002-8246-fd878a316e5a",
    "account_id": "29d8f709-...",
    "type": "credit",
    "amount": 100,
    "description": "Salary",
    "reference_id": "ref-1",
    "created_at": "2026-10-27T12:47:37.168Z"
  },
  "balance": 100
}
```

- **credit**: balance = balance + amount
- **debit**: balance = balance − amount. Rejected with `422` if the balance is too low.

### 4.5 Transaction history — `GET /accounts/:id/transactions?page=1&limit=10`

| Query | Default | Rules |
|---|---|---|
| `page`  | 1  | Integer ≥ 1 |
| `limit` | 10 | Integer from 1 to 100 |

Results are sorted **latest first** by `created_at`.

Response `200 OK`:
```json
{
  "data": [ { "id": "...", "type": "credit", "amount": 100, "...": "..." } ],
  "pagination": {
    "page": 1,
    "limit": 10,
    "total_records": 1,
    "total_pages": 1
  }
}
```

Asking for a page past the end returns an empty `data` array (not an error).

### 4.6 Transfer money (bonus) — `POST /transfers`

Request:
```json
{
  "from_account_id": "A-id",
  "to_account_id": "B-id",
  "amount": 30,
  "description": "Rent share",
  "reference_id": "transfer-001"
}
```

Response `201 Created`:
```json
{
  "amount": 30,
  "reference_id": "transfer-001",
  "from_account": { "id": "A-id", "name": "A", "balance": 70, "created_at": "..." },
  "to_account":   { "id": "B-id", "name": "B", "balance": 80, "created_at": "..." },
  "debit_transaction":  { "type": "debit",  "amount": 30, "...": "..." },
  "credit_transaction": { "type": "credit", "amount": 30, "...": "..." }
}
```

A transfer creates two normal transactions: a debit on the source account and a credit on the destination account. Both use the same `reference_id`, so a transfer shows up in each account's history.

### 4.7 Health check — `GET /health`

Returns `{ "status": "ok" }`.

## 5. Errors

Every error has the same shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request data is invalid",
    "details": [
      { "field": "amount", "message": "amount must be greater than 0" }
    ]
  }
}
```

`details` appears only for validation errors.

| Status | `code` | When |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Missing or invalid fields (name, type, amount, reference_id, and so on), or the body is not a JSON object |
| 400 | `INVALID_JSON` | Body is not valid JSON |
| 400 | `INVALID_PAGINATION` | Bad `page` or `limit` |
| 404 | `NOT_FOUND` | Account (or route) does not exist |
| 405 | `METHOD_NOT_ALLOWED` | Trying to edit or delete a transaction |
| 409 | `DUPLICATE_TRANSACTION` | `reference_id` already used for this account |
| 422 | `INSUFFICIENT_BALANCE` | Debit or transfer is larger than the balance |
| 500 | `INTERNAL_ERROR` | Unexpected server error (details are logged, not exposed) |

## 6. Try it with curl

```bash
# create two accounts
curl -X POST localhost:3000/accounts -H "Content-Type: application/json" -d '{"name":"Alice"}'
curl -X POST localhost:3000/accounts -H "Content-Type: application/json" -d '{"name":"Bob"}'

# credit Alice (replace <ALICE_ID>)
curl -X POST localhost:3000/accounts/<ALICE_ID>/transactions -H "Content-Type: application/json" \
  -d '{"type":"credit","amount":100,"description":"Deposit","reference_id":"dep-1"}'

# transfer 30 from Alice to Bob
curl -X POST localhost:3000/transfers -H "Content-Type: application/json" \
  -d '{"from_account_id":"<ALICE_ID>","to_account_id":"<BOB_ID>","amount":30,"reference_id":"tr-1"}'

# history and balance
curl "localhost:3000/accounts/<ALICE_ID>/transactions?page=1&limit=10"
curl localhost:3000/accounts/<ALICE_ID>/balance
```

## 7. Assumptions

1. **Single currency.** Amounts have at most 2 decimal places and are stored as integer cents.
2. **Duplicate `reference_id` returns `409 Conflict`.** It is not treated as a silent idempotent replay, and the balance is not changed. The same `reference_id` may be used on **different** accounts.
3. **Insufficient balance returns `422 Unprocessable Entity`.** The request is valid, but the business rule rejects it. Balances can never go below 0 (no overdraft).
4. **IDs are UUIDs** generated by the server. Timestamps are ISO-8601 in UTC.
5. **`description` is optional.** For transfers without one, a default such as "Transfer to <id>" is used.
6. **Sorting tie-break:** if two transactions have the same `created_at`, the one inserted later comes first.
7. **Transfers** use the same `reference_id` on both legs. A transfer to the same account is rejected (`400`).
8. **No authentication.** It was not part of the assignment.
9. **Concurrency:** `better-sqlite3` runs every database transaction synchronously in one Node process, so two requests can't interleave inside a transaction. The guarded `UPDATE ... WHERE balance >= ?` and the DB constraints would still protect the data if this were moved to a multi-process database.
10. **Account listing, updating and deleting** were not required, so they are not implemented.
